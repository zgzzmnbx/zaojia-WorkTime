# Opus 任务包契合度评审

版本 1.0.0 · 2026-11-06

结论：适合作为“跨项目工日容量初筛”的算法素材，不足以作为领导要求的人员投入与实施费结算核验完整任务包。应保留有效的窗口筛查、唯一身份、重复提示、证据解释和模拟案例，补齐业务主线后实施。

## 对照依据与限制

依据为 `00-初版任务包/任务书01_人员工时与实施费结算核验.txt` 与 `opus初版任务包-工时合规校验_任务包_v3 (1).md`。本目录未提供任务书所引两份会议原文或录音，未独立复核从录音到任务书的转写准确性。Opus 标注日期早于任务书，且自称规则“已定”；这些字样不构成业务授权证据。用户本轮明确阈值尚未确认。

## 算法与代码复核

1. 原包两个 Python 代码块提取到 `Codex-Temp/opus-review/`，实际运行得到 20 PASS、0 FAIL。T6 不在原脚本中，不能说全部界面和功能均已测试。脚本的 `ok` 只打印 FAIL，不会因此退出失败，正式测试应使用断言。
2. 重复情景缺陷已复现：同项目同期间三条 10、5、10 工日，中间 5 已明确追加，末条待核。原 `apply_once` 整组取最大只留 10，连已确认追加也删去。改进：已确认追加保留；其余待核组给出明确假设的情景值，最终仍须逐条认定。
3. 输入缺陷已复现：单位为“人月”时原参考代码直接当工日；NaN 未进无法校验列表而得到红色。界面可能另行限制，但逻辑基准本身未封口。需严格单位白名单和有限数校验。
4. C2=max(n,C1) 不可加：2026-03-02～06 为 5.74013，03-07～08 为 2，合起来 03-02～08 却为 7。不能把基于可加每日容量的充分必要性结论直接扩展到 C2。原 T12 验证的是模型自身分级，不是实际调度不可能的证明。
5. C2 取最大值不是“每天8小时再加满加班额度”的相加模型。统一称“模拟高负荷参考线”，取消“物理不可能”“法定全勤上限”“至少必须核减”等过度结论。实际重叠、容量不足、合同不予认定是三个不同层次。
6. 36小时/月与按 n/30.4 折算并不等价；原包也没有覆盖每日限制、适用工时制度及例外。劳动法条款不是项目结算计量规则。仅保留为有标签的模拟参数，不自动出法律结论或正式审减。
7. 日历缺失并非总是偏宽松：缺调休补班也可能低估容量。改为“按周一至周五估算，可能高估或低估”。日期放宽跨年需同步检查日历完整性。
8. 全部条目平均摊到每日后画红色负荷会制造事实感；首版改用原申报期间条带，明确显示总量，不生成假定每日工时。风险分和“高职称多头挂名”无业务依据，首版不启用。
9. 时间复杂度不仅是窗口数 k²；每个窗口再扫描条目、归因逐步重算及逐日算容量还会增加成本。原包的 1000人×50条、5秒目标尚无性能证据。
10. `submitted_at`、`entered_at`、`created_at` 混用，申报顺序也不等于认定先后。应分别保存事实日期与系统处理事件。

劳动法核查来源：[国家市场监督管理总局公布的《中华人民共和国劳动法》](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_d9aa750028b14b99a776cb93726a360d.html)，第41条规定日与月的延长工时限制，第42条另列例外；本工具不据此判定合同结算合法性。
